# 開発ワークフロー仕様

## 1. 目的

この文書は、Claude Code で Issue 起点の開発を行うための運用仕様です。Issue は人間と Claude が同じ要求を参照するための実装契約として扱います。

- 人間: Claude の判断と実装結果を後から理解できる
- Claude: Issue から対象範囲、完了条件、検証方法を一貫して読み取れる
- GitHub: 要求、レビュー、履歴を保管する

## 2. コマンドと責務

| コマンド | 入力 | 責務 | 副作用 |
| --- | --- | --- | --- |
| `/01` | Issue タイトル | 調査済みの Issue を作成する | GitHub Issue を作成する |
| `/11` | Issue 番号 | Issue 用ブランチを作成または再利用し、Issue の実装と検証を行う | Git branch とコード・仕様・テストを変更する |
| `/21` | Issue 番号 | 対象変更だけを検証してコミットする | Git commit を作成する |
| `/31` | Issue 番号 | コミット済みの Issue 用ブランチから Pull Request を作成する | GitHub Pull Request を作成する |
| `/41` | バージョン、リリース Issue 番号(任意) | `main` から配布物を作り、WordPress.org の SVN trunk へ反映する準備をする。公開後は状態を確認して Issue に記録する | SVN の作業コピーを変更する。Issue にコメントし、閉じる場合がある |

`/01` は実装を行いません。`/11` はコミットを行いません。`/21` は Issue と無関係な変更をコミットしません。`/31` は未コミット変更を勝手にコミットしません。`/41` は `svn commit` を実行しません。

## 3. Issue タイトル

入力されたタイトルは要求の要約として使用します。Claude は意味を変えない範囲で、タイトルを次の形式へ正規化してよいものとします。

```text
<type>: <具体的な変更または解決したい状態>
```

`type` は次のいずれかです。

- `feat`: 利用者向け機能追加・変更
- `fix`: 不具合修正
- `docs`: ドキュメント変更
- `refactor`: 外部動作を変えない構造改善
- `test`: テスト追加・改善
- `chore`: 開発環境・保守作業

タイトルは短く、実装手段ではなく達成したい状態を表します。入力タイトルが十分に具体的な場合は、無理に変更しません。内容が複数の独立した要求に分かれる場合は、Issue を分割する提案を優先します。

## 4. Issue 本文の正規形式

`/01` が作成する本文は、次の見出し順を必ず守ります。見出しを省略せず、該当しない場合は `N/A` と記載します。

```markdown
## 要約

<!-- 1〜3文。誰の、どの問題を、どの状態にするか。 -->

## 種別

- Type: feat | fix | docs | refactor | test | chore
- Scope: 対象モジュール、画面、API、またはドキュメント
- Priority: low | medium | high

## 背景

<!-- この変更が必要になった理由。観測できる事実を中心に書く。 -->

## 現状と課題

<!-- 現在の挙動、問題、再現条件、制約。推測は「仮説」と明記する。 -->

## 目的

<!-- この Issue 完了後に利用者またはシステムがどうなるか。 -->

## 対象範囲

### 対象

- [ ] この Issue で変更するもの

### 対象外

- この Issue では変更しないもの

## 対応方針

<!-- 既存仕様との整合性、主な実装方針、データ/API/画面への影響。 -->

## 受入条件

- [ ] 具体的な動作条件。確認方法が明確である
- [ ] 既存機能への影響を確認する
- [ ] 必要なテスト・診断・手動確認を完了する

## 検証方法

| ID | 条件 | 方法 | 合格基準 |
| --- | --- | --- | --- |
| V-01 |  |  |  |

## 依存関係

- Depends on: N/A
- Related to: N/A
- Conflicts with: N/A

## 未決事項

- N/A

## 参考

- 仕様書: `spec/SPECIFICATION.md`
- 関連ファイル、URL、スクリーンショットなど
```

## 5. 記述ルール

### 5.1 Claude が判断してよいこと

- 種別、Scope、Priority の分類
- 関連する仕様書・実装・テストの特定
- 実装方針の候補整理
- 受入条件を検証可能な表現への変換
- Issue タイトルの軽微な正規化

判断した場合は、本文の「対応方針」または「未決事項」に理由を記載します。

### 5.2 Claude が推測してはいけないこと

次の情報が不足している場合、Claude は Issue を作成せず確認を求めます。

- 何を解決したいのかが特定できない
- 受入条件を検証可能な形にできない
- 複数の要求が矛盾している
- 破壊的変更、公開 API 変更、データ移行の要否が不明
- ユーザーの意図を変えるタイトルの正規化が必要

### 5.3 受入条件のルール

受入条件は、実装手段ではなく観測可能な結果で書きます。次のような抽象的な条件だけでは不十分です。

```text
- [ ] いい感じに動く
- [ ] 必要な修正を行う
```

次の情報を含めます。

- 対象: 画面、API、投稿、ファイルなど
- 操作または入力
- 期待する結果
- 例外または既存機能への影響

## 6. `/01` の作成手順

1. 入力タイトルを検証する
2. Git リポジトリ、作業ツリー、仕様書、関連コードを確認する
3. GitHub の既存 Issue を検索する
4. 種別、Scope、Priority、背景、課題、対象範囲を整理する
5. 受入条件を検証可能な箇条書きへ分解する
6. 検証方法を `V-01` 形式の表にする
7. 未決事項があれば明記する
8. `gh auth status` を確認する
9. 正規形式の本文で Issue を作成する
10. Issue 番号、URL、判断した事項、未決事項を報告する

## 7. `/11` と `/21` への引き継ぎ

`/11` は次の見出しを実装の入力として扱います。

- `## 目的`
- `## 対象範囲`
- `## 対応方針`
- `## 受入条件`
- `## 検証方法`
- `## 未決事項`

`/11` は未決事項が実装判断に影響する場合、勝手に補完せず停止します。`/21` は Issue 番号とコミット対象の変更を照合し、受入条件と検証結果が確認できた場合だけコミットします。

## 8. `/11` 実装仕様

### 8.1 入力

`/11` は 1 件以上の Issue 番号を受け取ります。空白、`,`、`、` を区切りとして扱い、`#` は除去します。番号がない、不正な文字がある、重複している場合は、それぞれ停止・除去・重複排除して結果を報告します。

### 8.2 開始条件

- 指定したすべての Issue を取得できる
- Issue が `## 目的`、`## 対象範囲`、`## 受入条件`、`## 検証方法` を含む
- 既存の未コミット変更を確認し、今回の Issue と競合しない
- 複数 Issue の依存関係と要求が矛盾しない
- 変更前に、受入条件を確認できる最小の検証方法を決められる
- Issue 用ブランチの作成または再利用が完了している

開始条件を満たさない場合はコードを変更しません。未決事項が実装判断に影響する場合も同様です。

### 8.3 実装ルール

- `CLAUDE.md`、本仕様書、`spec/SPECIFICATION.md` の順序ではなく、内容の責務に応じてすべて確認する
- 既存の抽象化、WordPress 標準 API、既存テストを優先する
- Issue の対象外を変更しない
- 仕様変更を伴う場合は `spec/SPECIFICATION.md` を更新する
- ユーザーの未コミット変更を破棄・上書きしない
- コミット、PR 作成、Issue の自動クローズは行わない

Issue の実装に着手する前に、`/11` は作業ツリーがクリーンであることを確認します。現在のブランチがデフォルトブランチの場合は、リモートの最新状態を取得して fast-forward 更新した後、`issue/<number>-<slug>` ブランチを作成して切り替えます。複数Issueの場合は番号を連結します。既に対象Issue用ブランチにいる場合は再利用し、無関係なブランチや未コミット変更がある場合は停止します。ブランチ作成または再利用の完了後に、コード・仕様・テストの編集を開始します。

実装と検証が完了したら、`gh issue comment <number> --body-file -` で対象 Issue に実装結果をコメントする。コメントには実装内容、変更ファイル、受入条件の判定、検証結果、未解決事項を含める。コメント投稿に失敗した場合は、実装結果の報告に失敗理由を記載する。

### 8.4 完了条件

各 Issue の受入条件を、次の形式で 1 件ずつ判定できることを完了条件とします。

| Issue | 条件 ID | 結果 | 根拠 |
| --- | --- | --- | --- |
| #12 | AC-01 | PASS / FAIL / BLOCKED | 変更ファイル、画面、テスト、コマンド |

`FAIL` または `BLOCKED` がある場合、実装完了とは報告しません。

### 8.5 `/11` の報告形式

```markdown
## 実装結果

### 対象 Issue

- #12: タイトル

### 変更ファイル

- `path/to/file`: 変更理由

### 受入条件

| Issue | 条件 ID | 結果 | 根拠 |
| --- | --- | --- | --- |
| #12 | AC-01 | PASS | `command` の結果 |

### 検証

- PASS: `command`
- PASS: 画面/API/手動確認

### 未解決事項

- N/A
```

## 9. `/21` コミット仕様

### 9.1 入力と開始条件

`/21` は 1 件以上の Issue 番号を受け取ります。Issue 番号の解釈は `/11` と同じです。

開始前に次を確認します。

- 対象 Issue を取得できる
- `git status --short`、`git diff`、`git diff --cached` を確認できる
- 対象変更と Issue の対応をファイル・差分単位で説明できる
- 受入条件と検証結果が確認できる
- 対象外の変更、機密情報、一時ファイルがステージされていない
- 原則として Issue 用ブランチ上である。デフォルトブランチ `main` 上の場合は、明示的な許可がない限りコミットしない

### 9.2 ステージルール

- `git add -- <明示したパス>` のみを使用する
- `git add .`、`git add -A`、全ファイル指定を使用しない
- 同一ファイル内に対象変更と対象外変更が混在し、安全に分離できない場合は停止する
- 既にステージ済みの変更が対象 Issue と対応しない場合は、変更せず報告する
- `git diff --cached` を読み、コミット対象を人間が追跡できる状態にする

### 9.3 複数 Issue

- 独立した Issue は Issue ごとに分けてコミットする
- 強く結合して分離できない場合だけ、1 コミットにまとめる
- まとめる場合は、コミットメッセージに全 Issue 番号を含める
- 要求が矛盾する場合はコミットしない

### 9.4 コミット条件

次をすべて満たす場合だけコミットします。

- 対象 Issue、変更ファイル、受入条件の対応が説明できる
- 関連する診断・テストが PASS している
- `git diff --cached --check` が PASS している
- Conventional Commits 形式のメッセージに Issue 番号が含まれる

例:

```text
fix: resolve consultation event detail links (#12)
feat: add event filtering (#12, #15)
```

### 9.5 `/21` の報告形式

```markdown
## コミット結果

### 対象 Issue

- #12: タイトル

### コミット

- Commit: `abc1234`
- Message: `fix: ... (#12)`

### 対象変更

- `path/to/file`: Issue との対応

### 検証

- PASS: `git diff --cached --check`
- PASS: `command`

### 残った未コミット変更

- N/A
```

コミットしなかった場合は「コミット結果」と書かず、「コミット停止理由」として不足条件、対象ファイル、次に必要な判断を報告します。

## 10. 変更履歴と PR

`/21` でコミットした後の PR 作成は `/31 <Issue番号>` で行います。`/31` は Issue 用ブランチ、未コミット変更、ベースブランチとの差分、既存PRを確認し、問題がなければ GitHub Pull Request を作成します。Issue、コミット、PR の番号や URL を報告に含め、後から要求から実装まで追跡できるようにします。

`/31` は次の条件を満たさない場合、変更を破棄・退避・コミットせず停止します。

- 現在のブランチがデフォルトブランチではない
- 作業ツリーに未コミット変更がない
- Issue に対応するコミットがベースブランチより先行している
- 同じ Issue または head ブランチのオープンな PR が存在しない

## 11. 機密情報

Issue にはパスワード、トークン、個人情報、ローカル固有の絶対パス、未公開の秘密情報を記載しません。ログやスクリーンショットを参照する場合は、機密部分を除去します。

## 12. WordPress.org へのリリース

リリースは、バージョン更新までを Issue 起点の通常の流れ(`/01` → `/11` → `/21` → `/31`)で行い、それ以降を `/41` で行います。

### 12.1 バージョン更新(`/01`〜`/31`)

リリース用の Issue を作成し、次の 5 か所のバージョン表記を同じ値に更新します。`readme.txt` の Changelog に、新バージョンの項目を英語で追加します。

- `ototsugu-connector.php` の `Version`
- `readme.txt` の `Stable tag`
- `spec/SPECIFICATION.md` の現行バージョン
- `blocks/event-list/editor.asset.php` の `version`
- `includes/class-single-event.php` のスタイルのバージョン文字列

リリース Issue は SVN への反映が終わるまで閉じません。PR の本文は、`Fixes #<number>` の代わりに `Refs #<number>` とします。

### 12.2 `/41` の段階

`/41 <バージョン> [#Issue番号]` は、`https://plugins.svn.wordpress.org/<スラッグ>/tags` に `<バージョン>` があるかで段階を判定します。

| 段階 | 条件 | 内容 |
| --- | --- | --- |
| 1: 準備 | tag がない | `main` から配布物を作り、SVN の trunk へ反映して、利用者が実行するコマンドを示して停止する |
| 2: 確認と記録 | tag がある | SVN、Stable tag、WordPress.org の API と公開ページを確認し、Issue に記録する。すべて確認できた場合のみ Issue を閉じる |

開始前に、`origin/main` の 5 か所のバージョン表記が指定のバージョンであることを確認します。異なる場合は停止します。

### 12.3 段階 1 の作業

- 配布物は `git archive origin/main` の内容から、`.distignore` に書かれたものを除いて作る。作業は一時ディレクトリの中で行う
- SVN の作業コピーは、このリポジトリの隣の `svn-<スラッグ>` を既定とし、作業前に `svn status` が空であること、`assets` の下などにリポジトリ全体の入れ子チェックアウトがないことを確認する
- trunk への反映は、PowerShell で `robocopy /MIR /XD .svn` と `svn add --force trunk` を実行する
- `svn commit` は、SVN のパスワード入力が必要なため、利用者が自分の端末で実行する。Claude は実行しない
- tag(`svn cp trunk tags/<バージョン>`)は、trunk のコミットが成功してから作る

利用者が実行するコマンドの順序は次のとおりです。

```text
svn commit trunk -m "Version <バージョン>" --username <SVNユーザー名>
svn update
svn cp trunk tags/<バージョン>
svn commit tags/<バージョン> -m "Tagging version <バージョン>" --username <SVNユーザー名>
```

### 12.4 リリース後

- 公開ページと API の反映には時間がかかることがある。反映が確認できるまで、リリース Issue は閉じない
- 翻訳を受け付けている場合は、translate.wordpress.org での翻訳の登録が必要かを確認する
